# PostgreSQL Setup

PostgreSQL is Stitchd's primary OLTP store. It holds every piece of
configuration that backend services need to make a flag-evaluation, segment
lookup, or experiment lifecycle decision:

- Organisations, projects, environments, and SDK-key hashes
  (`stitchd-auth-service`).
- Feature flags, variants, rule lists, default-rule percentage
  distributions (`stitchd-flag-service`).
- Segment definitions, rule trees, and the
  `segmentation-service`-owned metadata sidecar for list segments — the
  list memberships themselves live in ScyllaDB (see
  [`./scylladb.md`](./scylladb.md)).
- Event definitions, metric definitions, audit log, and the experiment
  lifecycle tables (`stitchd-experimentation-service`,
  `stitchd-analytics-service`).
- Auth state: users, refresh tokens, MFA enrolments, invitations
  (`stitchd-auth-service`).

All queries go through the [`sqlx`](https://docs.rs/sqlx/) `query!` /
`query_as!` macros, which are checked against a live database at compile
time. The offline cache lives at `.sqlx/` and is regenerated by
`cargo sqlx prepare --workspace`.

## System Requirements

- PostgreSQL 16 (matches the `postgres:16-alpine` image in
  `docker-compose.yml`).
- A single database owned by a single Stitchd role. There is no schema-level
  multi-tenancy — tenancy is enforced at the row level via
  `organisation_id` / `environment_id` columns and at the gRPC layer.

## 1. Provision the Database

For local dev the compose file does this for you (image
`postgres:16-alpine`, env `POSTGRES_USER` / `POSTGRES_PASSWORD` /
`POSTGRES_DB`).

For a self-managed deployment:

```sql
CREATE ROLE stitchd LOGIN PASSWORD 'your-strong-password';
CREATE DATABASE stitchd OWNER stitchd;
```

The role does not need `SUPERUSER`, but it must own the database so
`sqlx migrate run` can `CREATE TABLE` and `CREATE INDEX`.

## 2. Run Migrations

Migrations live in
[`crates/stitchd-db/migrations/`](https://github.com/stitchd-dev/feature-flag/tree/main/crates/stitchd-db/migrations)
and are stamped `YYYYMMDDhhmmss_<name>.sql`. They are managed by
[`sqlx-cli`](https://docs.rs/crate/sqlx-cli/) and applied in filename
order.

```bash
# sqlx-cli requires a plain DATABASE_URL env var. Alias from STITCHD_DATABASE_URL.
export STITCHD_DATABASE_URL="postgres://stitchd:your-strong-password@localhost:5432/stitchd"
export DATABASE_URL="$STITCHD_DATABASE_URL"

# Install sqlx-cli if needed (one-time).
cargo install sqlx-cli --no-default-features --features rustls,postgres

# Apply all pending migrations. Idempotent — already-applied migrations are
# skipped via the _sqlx_migrations tracking table.
sqlx migrate run --source crates/stitchd-db/migrations
```

The `DATABASE_URL` alias is the one wart in the bootstrap sequence — every
Stitchd-owned environment variable carries the `STITCHD_` prefix
([`./env-vars.md`](./env-vars.md)), but `sqlx-cli` insists on the unprefixed
`DATABASE_URL`. The pattern is documented in `conductor/workflow.md` and the
root [`README.md`](https://github.com/stitchd-dev/feature-flag/blob/main/README.md).

### What the migration set creates

Notable groups, in chronological order:

| Phase                         | Migrations                                                  | What lands                                                                          |
|-------------------------------|-------------------------------------------------------------|-------------------------------------------------------------------------------------|
| Initial tenancy + RBAC        | `20260411000001_*` … `20260411000006_*`                     | `organisations`, `projects`, `environments`, `sdk_keys`, `users`, `audit_log`.      |
| Flags + segments              | `20260411000004_*`, `20260412000001_*`, `20260412000002_*`  | `feature_flags`, `variants`, `segments`, `segment_rules`. (List entries were here.) |
| Experimentation foundations   | `20260419000001_*` … `20260420000001_*`                     | `event_definitions`, `experiments`, `experiment_iterations`.                        |
| Auth (refresh, OIDC, SAML)    | `20260421000001_*`, `20260421000002_*`                      | `refresh_tokens`, MFA tables, system-org flag.                                      |
| Performance indexes           | `20260516000001_*` … `20260516000004_*`                     | Covering indexes on `sdk_keys.key_hash`, soft-delete partials, etc.                 |
| ScyllaDB cutover              | `20260516000005_drop_segment_list_entries.sql`              | Removes the PG `segment_list_entries` table — list memberships moved to Scylla.     |
| Stats / metric cutover        | `20260519000001_*` … `20260520000004_*`                     | Drops the PG `experiment_results` (now in CH); adds `metric_definitions`.           |
| Experiment attribution        | `20260521000001_*` … `20260521000004_*`                     | Attribution fields, `feature_flags.default_rule_distribution`, the active-iteration view. |

The last entry — `20260521000004_v_experiment_iterations_active.sql` — creates
the PostgreSQL view that the ClickHouse `experiment_iterations_active`
dictionary pulls from. ClickHouse migrations will fail their first dictionary
reload if Postgres is not migrated yet.

## 3. Connection String

```
postgresql://[user]:[password]@[host]:[port]/[database]
```

Set as `STITCHD_DATABASE_URL`. Every backend service that touches PostgreSQL
reads this variable; there is no per-service override. Example for the
compose stack:

```
postgresql://stitchd:stitchd@localhost:5432/stitchd
```

The dev defaults are baked into the
[`docker-compose.yml`](https://github.com/stitchd-dev/feature-flag/blob/main/docker-compose.yml)
service environment blocks — backend services see
`postgresql://stitchd:stitchd@postgres:5432/stitchd` (the `postgres` hostname
is resolved by the `stitchd` Docker network).

## Connection Pooling

Each service constructs a `sqlx::PgPool` at startup with default pool
sizing (10 connections). With six backend services in the default topology
you should size `max_connections` on the Postgres side to at least
`6 × 10 = 60`, with headroom for `sqlx-cli` and ad-hoc psql sessions. For
HA / multi-replica deployments multiply by the per-service replica count.

## Backup & Maintenance

Stitchd makes no Postgres-specific assumptions: take logical backups with
`pg_dump`, ship WAL with `pg_basebackup` + archiving, or use whatever
managed-Postgres flow your platform exposes. The audit log
(`audit_log` table, growing monotonically with every mutating admin
request) is the only table that typically dwarfs the rest by row count —
plan VACUUM / partitioning if you keep audit retention long.
