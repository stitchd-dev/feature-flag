# Gateway

`stitchd-gateway` is the only network-attached process clients ever speak to. It
terminates **HTTP** (admin UI, CLI, SDK telemetry) and **gRPC** (SDK definition
sync, eval-log ingest), authenticates the caller at the edge, and proxies every
request to the correct internal gRPC service over a tonic channel.

The gateway is **lean**: post-`gateway_lean_20260518` it owns no database
connection — no PostgreSQL, no ClickHouse, no Redis. Every byte of persisted
state lives behind one of the downstream services. If the gateway crashes you
restart it; if a service crashes the gateway proxies the next request and
returns `502` until the service comes back.

## What it does

- **Authenticates every request** at the edge against `stitchd-auth-service`
  via `ValidateCredential`. The auth service caches SDK-key lookups
  (`SdkKeyCache` from `db_optim_20260516`), so the hot path is sub-millisecond
  after the first hit.
- **Proxies to one or more services** per request. Most routes are 1:1 — a flag
  list call fans out to `FlagService.ListFlags` and nothing else. A few admin
  views (experiment results, eval-stats) join data from multiple services.
- **Hosts SDK telemetry** on both REST and gRPC. The REST surface under
  `/v1/sdk/` accepts batched segment-membership and eval-log calls; the gRPC
  surface on port `50050` hosts `SdkService::SyncDefinitions` for the
  streaming flag/segment sync used by the Rust SDK.
- **Owns the OpenAPI contract.** Every admin/SDK route is annotated with
  `#[utoipa::path]` and re-exported through `ApiDoc` in
  `crates/stitchd-gateway/src/openapi.rs`. The committed
  `docs/src/api/openapi.json` is regenerated by `cargo xtask docs`.
- **Exposes Prometheus metrics** at `GET /metrics` (Prometheus text format,
  no auth) on the same port as the REST API. The `/v1/metrics` namespace is
  reserved for the metric-definitions CRUD surface.

## Ports

| Protocol  | Default | Env var                       | Purpose                                                            |
|-----------|---------|-------------------------------|--------------------------------------------------------------------|
| HTTP/REST | `8080`  | `STITCHD_GATEWAY_HTTP_PORT`   | Admin UI, CLI, SDK telemetry (`/v1/sdk/*`), `/metrics` exposition  |
| gRPC      | `50050` | `STITCHD_GATEWAY_GRPC_PORT`   | `SdkService::SyncDefinitions` + `IngestSdkEvalLog` for SDK clients |

Both listeners start in `main.rs` and run on the same tokio runtime.

## Auth surfaces

The gateway exposes **two** auth schemes, and the path prefix tells you which
one applies.

### 1. `x-sdk-key` — SDK telemetry

Used by the embedded SDK (`sdks/rust/`). The SDK sends an environment-scoped
key in the `x-sdk-key` header (REST) or gRPC metadata (sync stream). The
gateway resolves the key through `AuthService::ValidateCredential`, builds an
`SdkContext` (env_id + org_id + sdk_key_id), and stamps the resolved
`environment_id` onto every downstream call as `x-env-id` metadata. The
backend services trust that metadata and never see the raw SDK key.

Routes:

- `POST /v1/sdk/segments/list:batch`
- `POST /v1/sdk/events:batch`
- `POST /v1/events/track` (the SDK `Client::track()` admin-defined-event API;
  body capped at 5 MiB, per-env rate-limited by
  `STITCHD_EVENT_QUOTA_PER_SEC`, default `1000`)
- gRPC `SdkService::SyncDefinitions` on port `50050`
- gRPC `SdkService::IngestSdkEvalLog` on port `50050`

SDK routes **reject bearer tokens** — even a valid admin JWT gets `401` if
`x-sdk-key` is absent. See [SDK APIs](./sdk-api.md).

### 2. `Authorization: Bearer <jwt>` — admin / CLI

Used by the Admin UI and CLI. The JWT is obtained from
`POST /v1/auth/login` (or OIDC / SAML SSO) and validated through
`AuthService::ValidateCredential`. The resolved `RbacContext` is attached as a
request extension; downstream handlers read `tenant_id`, `subject`,
`is_system`, and the granted roles/permissions off it.

Two sub-trees enforce additional guards:

- `/v1/superadmin/*` requires `is_system = true` (System-org users only —
  used to provision tenant orgs).
- `/v1/management/*` requires `is_system = false` (only real-tenant users can
  manage their own projects/envs/SDK keys).

The full set of resource routes (flags, segments, events, metrics,
experiments, stats) lives outside both sub-trees on a plain JWT middleware.
See [Admin & Management APIs](./admin-api.md).

### Public routes (no auth)

- `GET  /v1/health` — liveness probe.
- `POST /v1/auth/login`, `POST /v1/auth/refresh`, plus the OIDC/SAML
  authorize/callback endpoints.
- `GET  /metrics` — Prometheus exposition.

## Service topology

Every authenticated request fans out to one or more of these services. The
gateway holds long-lived tonic `Channel`s to each one, configured via
environment variables:

| Service                          | Default addr             | Env var                                  | What the gateway calls into                                                                |
|----------------------------------|--------------------------|------------------------------------------|--------------------------------------------------------------------------------------------|
| `stitchd-auth-service`           | `localhost:50051`        | `STITCHD_AUTH_SERVICE_ADDR`              | Login, JWT refresh, OIDC/SAML, `ValidateCredential` (every request), org/project/env mgmt, auth-provider CRUD |
| `stitchd-flag-service`           | `localhost:50052`        | `STITCHD_FLAG_SERVICE_ADDR`              | Flag CRUD, rules/variants, hashing config, `EvaluatePreview`, eval-log SDK backend         |
| `stitchd-segmentation-service`   | `localhost:50053`        | `STITCHD_SEGMENTATION_SERVICE_ADDR`      | Segment CRUD, list-entry patches, batch list-membership for SDKs                           |
| `stitchd-analytics-service`      | `localhost:50054`        | `STITCHD_ANALYTICS_SERVICE_ADDR`         | Event-definition CRUD, `TrackEvents` ingest, metric-definitions, eval-stats, context registry |
| `stitchd-experimentation-service`| `localhost:50055`        | `STITCHD_EXPERIMENTATION_SERVICE_ADDR`   | Experiment CRUD, iterations, transitions, exposures, results bundles                       |
| `stitchd-stats-service`          | `localhost:50056`        | `STITCHD_STATS_SERVICE_ADDR`             | Out-of-band stats recompute, time-series, job-status polling                               |

`stitchd-auth-service` actually hosts **four** tonic services on the same
port — `AuthService`, `ManagementService`, `AuthProviderService`,
`OidcLoginService`, `SamlLoginService` — and the gateway holds a separate
client handle for each, all multiplexed onto the same channel.

> **The event-service is retired.** Post-`gateway_lean_20260518`, all
> event-ingest responsibilities moved to `stitchd-analytics-service`. There is
> no `STITCHD_EVENT_SERVICE_ADDR`; older deployment configs that set it can
> drop the variable.

## Error envelope

REST errors render as JSON. Auth failures return:

```json
{ "error": "invalid_sdk_key", "message": "SDK key is invalid, revoked, or unknown" }
```

Upstream gRPC errors are mapped to HTTP via `crate::error::GatewayError`:

| gRPC status         | HTTP status |
|---------------------|-------------|
| `UNAUTHENTICATED`   | 401         |
| `PERMISSION_DENIED` | 403         |
| `NOT_FOUND`         | 404         |
| `INVALID_ARGUMENT`  | 400         |
| `FAILED_PRECONDITION` | 409 (e.g. `flag_locked_by_experiment`) |
| `UNAVAILABLE`       | 502         |
| `INTERNAL`          | 500         |
